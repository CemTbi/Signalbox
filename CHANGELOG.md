# Changelog

All notable changes to Signalbox are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/). Before 1.0, minor versions may contain breaking changes, always with migration notes.

## [Unreleased]

### Added

- The service graph: a worker builds who called whom from the spans, a minute at a time, about two minutes behind: calls between services, and to databases and hosts outside the traced services, with their rate, errors and latency. The Traces page's Services view shows each service's requests, its operations, and the calls between them. `/api/v1/environments/{environmentId}/graph` and `/api/v1/environments/{environmentId}/operations` do the same through the API. The `worker` role is now available and part of `--roles=all`.
- Traces can be read. A project's Traces page searches an environment's traces by service, operation, errors, duration and attribute, and opens each as a waterfall: spans in tree order with their services' colors, durations and the critical path, and every span's attributes, resource and events. Requests Signalbox sends, from the Requests page, collection runs, `signalbox test run` and agents, carry a W3C `traceparent` header, unless they set their own or an empty one; their responses and run steps have Open trace, which finds the trace in whichever of the project's environments it arrived. `/api/v1/environments/{environmentId}/traces`, `/api/v1/environments/{environmentId}/services` and `/api/v1/projects/{projectId}/traces/{traceId}` do the same through the API, and history entries and run steps have `traceId`.
- The demo shop: `deploy/compose/compose.demo.yaml` adds a small web shop to the Compose stack, whose storefront, orders, inventory and payments services send real traces to Signalbox over OTLP, while shoppers browse and buy a few times a second. A seed sets it up through the API, with its services, published specs and an ingest key. Payments has a chaos switch that makes it slow, failing or unhealthy. See `examples/demo-shop/README.md`.
- Signalbox receives traces. Services send spans with any OpenTelemetry SDK or Collector over OTLP/gRPC (port 4317) or OTLP/HTTP (`POST /v1/traces` on port 4318, protobuf or JSON), or with Zipkin instrumentation (`POST /api/v2/spans` on port 9411, JSON or protobuf), and Signalbox stores them in ClickHouse. Each request carries an ingest key, made on a project's Ingest keys page or with `/api/v1/environments/{environmentId}/ingest-keys`, which decides the environment its spans land in; owners and admins manage keys. A request is answered once its spans are stored, and refusals say whether to retry, as each protocol defines. Credentials in attributes and URLs are replaced by `•••` before anything is stored, spans are kept within OpenTelemetry's default limits, and each environment may send `SIGNALBOX_INGEST_SPANS_PER_SECOND` spans a second, 5,000 by default. The ingest role runs with `--roles=all`, or on its own; `SIGNALBOX_OTLP_GRPC_ADDR`, `SIGNALBOX_OTLP_HTTP_ADDR` and `SIGNALBOX_ZIPKIN_ADDR` move its listeners. The Compose stack publishes the three ports.
- Metrics: every `signalbox-server` process serves `/metrics` on its ops listener (`:9090`), in the Prometheus text format, for Prometheus, VictoriaMetrics, Grafana Alloy or the OpenTelemetry Collector to scrape. They count API requests by route and status, requests sent from the server and from agents by outcome, scripts and their time, agents online, test runs, the database pool, and the Go runtime. [ADR-0038](docs/adr/0038-metrics.md) lists them.
- The local agent: `signalbox agent --server … --token …` sends your requests from your own machine, so `localhost`, private networks and your VPN work. It opens no port: it asks the server for work over HTTPS, holding each request up to 25 seconds, and sends up to 8 requests at a time; `--deny` keeps requests from address ranges. Choose it under Run on, beside the environment in Requests or when you run a collection, and the requests, scripts' `pm.sendRequest` included, go from there. History and runs say which agent sent them. The Agents page lists yours, whether each is online, and how to start one. Only your own requests reach your agents. `/api/v1/agents` does the same through the API, and sends and runs take `agentId`.
- Spec engine (`pkg/specengine`): parses Swagger 2.0 and OpenAPI 3.0, 3.1 and 3.2; validates against the official JSON Schema for each version; resolves `$ref`s and detects circular references that can never end; lints with the recommended and OWASP API Security rule sets. Every diagnostic carries a line and column.
- CI templates for test suites: a GitHub Action, `CemTbi/Signalbox/actions/test`, installs a released CLI after checking its checksum, runs a Postman collection or a stored collection with `signalbox test run`, annotates failed requests and tests, adds a summary to the job's page and uploads the reports. A GitLab CI include, `ci/gitlab/signalbox-test.yml`, does the same with its JUnit report in merge requests. `signalbox test run --reporter github` writes the annotations and the summary.
- Contract tests: a spec page's Contract tests panel, or `POST /api/v1/versions/{versionId}/contract-tests`, makes a collection with a request per operation of a published version, filled from its examples, with a folder per tag. Each checks that its response has a documented status and a body matching the schema, as tests from `Contract`, wherever it runs, against any base URL. `baseUrl` defaults to the spec's server or the version's hosted mock. Generating again for a newer version replaces the generated requests and keeps the items, scripts and variable values people added.
- `signalbox test run` runs a collection's requests and tests. Offline, it runs a Postman collection file with an optional Postman environment file (`-e`), data file (`-d`) and `--env-var` overrides, and needs no server; requests may reach this machine and private networks, but not cloud metadata addresses unless `--allow` opens them. With `--server`, `--token` and `--collection`, it runs a stored collection on the server and follows it, and Ctrl-C cancels it there. Both print each request as it ends, write JUnit, JSON and HTML reports with `-r` and `-o`, and exit with 1 when something failed.
- The history list now shows why a request got no response.
- Collection runs: run a collection, or a folder of it, as a test suite from its Run action. Requests run in order with their scripts, any number of iterations, optionally once per row of a CSV or JSON data file, with a delay between requests and an option to stop at the first failure. Values scripts set carry from one request to the next, `pm.execution.setNextRequest` jumps or ends an iteration, and nothing is saved to the environment. The run's page follows it as it goes, shows each request's tests, console and the start of a failed response, and downloads JUnit XML, JSON or a self-contained HTML report. Runs run in the background, two at a time per server, at most 10,000 requests or an hour each, and are kept for 90 days. `POST /api/v1/collections/{collectionId}/runs` and `/api/v1/runs/…` do the same through the API.
- Scripts run when a request is sent: the collection's, each folder's and the request's pre-request scripts before it, and their test scripts after, in Signalbox's Postman-compatible sandbox. The editor has a Scripts tab, and the response shows each test's result and the console. A failing pre-request script stops the send and says why. Variables scripts set last for the send and aren't saved, since environments are shared.
- Postman and cURL import and export: import a Postman Collection v2.1 or v2.0 under Collections, with its folders, requests, auth, variables and scripts, after a report of anything that will run differently or was left out. Collections export back to v2.1 for Postman and Newman. Postman environment files merge into an environment, secrets staying secret. Import cURL pastes a command, such as a browser's Copy as cURL, into the editor. Collections now keep variables, which fill in `{{name}}` for their requests where the environment has none, and the scripts of collections, folders and requests.
- Request auth: requests send basic auth, a bearer token or an API key in a header or the query, from the editor's Auth tab, saved with the request. Variables are filled in first, so credentials can be secrets. History keeps the auth's type, never its credentials, and masks every credential it sent.
- Environment variables: each environment keeps variables, which fill in `{{name}}` in a request's URL, headers and body when it is sent with that environment, along with `{{$guid}}`, `{{$timestamp}}`, `{{$isoTimestamp}}` and `{{$randomInt}}`. The Requests page has an environment switcher and a variables editor. Secret variables are encrypted with a per-workspace key, never shown again, and replaced by `•••` in history, responses included. Set `SIGNALBOX_SECRET_KEY` (or `SIGNALBOX_SECRET_KEY_FILE`) to 32 random bytes in base64 to turn secrets on, and back it up. Names with no value are sent as typed and listed in the response.
- Collections: save requests in a project's collections and folders, then reopen, rename, save and delete them from the Requests page. Each item has its own ETag, so people editing different requests never conflict, and saving over someone's change says so. Items move through the API, ordered by fractional indexes.
- The API client's first page: each project's Requests page sends a request from the server and shows the response, with a timing breakdown (DNS, connect, TLS, first byte, download). Requests that get no response say why, such as a host that doesn't exist or a destination Signalbox refuses. Each person's history keeps 30 days of what they sent, without credential headers. Owners, admins and editors may send. The `runner` role is now part of `--roles=all`, and `SIGNALBOX_EGRESS_ALLOW` and `SIGNALBOX_EGRESS_DENY` adjust where it may send requests.
- Personal access tokens: create them under Access tokens, and send them as `Authorization: Bearer sbx_pat_…` to use the API as yourself without a browser. They expire (90 days by default, at most a year), are shown once and stored as hashes, record when they were last used, and can be revoked at once. Only the web app can create or revoke them.
- The project canvas shows the project's services, placed by hand: editors drag them, or move a selected one with the arrow keys, and the layout is saved for everyone. Arrange automatically lays the canvas out, and double-clicking a service opens it. New services take the next free spot. `PUT /api/v1/projects/{projectId}/canvas` moves services without changing their ETags.
- Published versions offer generated code as a zip, from the spec page or `GET /api/v1/versions/{versionId}/code?target=…`: a TypeScript client, a Go client or a Go server stub, with `WARNINGS.md` when the code can't express part of the spec. The same version always gives the same archive.
- `signalbox codegen --target typescript-client <file>` generates a TypeScript client with no dependencies, on `fetch`: a type per schema, and a method per operation that takes its parameters and body in one object, resolves to the success response's body, and throws `ApiError` for other statuses.
- `signalbox codegen --target go-client|go-server <file>` generates a Go client, or a Go server stub with typed requests and responses on `net/http`, with oapi-codegen. Several types in one schema and `const` are rewritten so the generator can express them, and the OpenAPI 3.1 and 3.2 features it can't express are reported with their lines; `--fail-on-warning` fails CI on them.
- `signalbox diff <base> <head>` reports what changed between two versions of an API: breaking changes as errors, changes that may break some clients as warnings, and the rest as information, each with its operation and line. Output is text, JSON, GitHub Actions annotations or a Markdown table, and the exit code fails CI on breaking changes. Signalbox's own CI reports changes to its API on every pull request.
- `signalbox lint` with text, JSON and GitHub Actions annotation output, `--fail-on` and `--min-severity` thresholds, and standard input support.
- `signalbox-server` with the `api` role: `/livez` and `/readyz` in `application/health+json`, `GET /api/v1/meta`, `POST /api/v1/spec-checks`, RFC 9457 error responses, request IDs, security headers, a separate ops listener and graceful shutdown with a drain delay.
- The platform's own API contract in `api/openapi.yaml`.
- Project governance, contribution guide, security policy, and the first eight architecture decision records.
- PostgreSQL storage. The server waits for the database, applies migrations at startup under an advisory lock, and reports each stage through `/readyz`. `signalbox-server migrate` runs migrations as a separate step.
- First-run setup: a new installation logs a setup code, and the setup page uses it to create the first admin account. `SIGNALBOX_SETUP_CODE` sets the code instead.
- Sign-in with email and password: Argon2id hashes, server-side sessions that end after 12 hours idle or 7 days, CSRF protection through the request origin and a per-session token, and rate limits per client address and per account.
- Workspaces with owner, admin, editor and viewer roles, and projects with development, staging and production environments, in the API and the web app. Edits use ETags and lists page with cursors.
- The web app now has sign-in, setup, workspace and project pages, an empty canvas for each project, and the spec check at `/spec-check`.
- Workspace members and invitations. Owners and admins create an invitation link for an email address and a role, and send it however they like; the invitee creates an account from it, or signs in and accepts. Members' roles can change, people can be removed or leave, and a workspace always keeps an owner.
- Single sign-on through an OpenID Connect provider, such as Okta, Microsoft Entra ID, Google, Keycloak or Dex. Someone signing in for the first time gets an account if the provider has verified their email address and no account has it; existing accounts are never taken over by email address. `SIGNALBOX_OIDC_ALLOWED_DOMAINS` limits which email domains get accounts. Invitation links work with single sign-on too.
- Reference docs: every published version has docs at `/specs/{specId}/docs`, with a version switcher. Operations are grouped by tag, with their parameters, bodies, responses and schemas, and the examples the mock sends. Each has code samples in cURL, JavaScript, Python, Go, Java and C#, for the mock or any of the API's servers, and a Try it form that calls the mock. `GET /api/v1/versions/{versionId}/reference` serves the same reference.
- Hosted mocks: every published version answers at `/mocks/{specId}/{version}`, or `/latest`, without sign-in and from any origin. Responses come from the spec's examples or are generated from its schemas, the same for the same request; requests are checked, and invalid ones get a problem naming the field. `Prefer: code=404` and `Prefer: example=name` choose the response. The spec page shows each version's mock address. The work a version's mock may take is bounded, so schemas that refer to one another many times can't exhaust the server.
- Published versions: publish a spec's revision under a name such as 1.4.0, with release notes, from the API or the spec's page. A revision with errors can't be published. Mocks, docs and code generation will serve published versions.
- Services and their specs in the web app: add services to a project, add a spec by pasting or uploading it, see its problems by line, edit it and save revisions with a note, and read its history. Viewers see everything read-only.
- Services and their OpenAPI specs in the API. Every save of a spec is a numbered revision that never changes, checked with the recommended rules, with its report, content and SHA-256. Saves need the spec's current ETag, so two people can't overwrite each other's work. Spec check reports now include the document's title and API version.
- New settings: `SIGNALBOX_DATABASE_URL`, `SIGNALBOX_PUBLIC_URL`, `SIGNALBOX_TRUSTED_PROXIES`, `SIGNALBOX_SETUP_CODE`, `SIGNALBOX_MIGRATE` and `SIGNALBOX_DATABASE_WAIT`; for single sign-on, `SIGNALBOX_OIDC_ISSUER`, `SIGNALBOX_OIDC_CLIENT_ID`, `SIGNALBOX_OIDC_CLIENT_SECRET` (or `SIGNALBOX_OIDC_CLIENT_SECRET_FILE`), `SIGNALBOX_OIDC_NAME`, `SIGNALBOX_OIDC_SCOPES`, `SIGNALBOX_OIDC_ALLOWED_DOMAINS` and `SIGNALBOX_OIDC_TRUST_UNVERIFIED_EMAIL`.

### Changed

- The server now needs ClickHouse, besides PostgreSQL, for spans and what's built from them. Set `SIGNALBOX_CLICKHOUSE_URL` before upgrading; the Compose stack already runs ClickHouse. The server migrates ClickHouse at startup like PostgreSQL, and `signalbox-server migrate` migrates both. `SIGNALBOX_TRACE_RETENTION_DAYS` sets how long spans are kept, 7 days by default. `make dev-db` now starts ClickHouse too.
- `POST /api/v1/spec-checks` now needs a signed-in session.
- The server now needs PostgreSQL. `make dev-db` starts one for development.

### Security

- go-jose 4.1.6 fixes a denial of service when parsing a JSON Web Key Set with RSA keys (GHSA-mgcc-cww5-fp2q), which an identity provider's keys endpoint could send. golang.org/x/net 0.62.0 fixes two flaws in its HTML parser.
- Adding a spec no longer freezes the browser tab on YAML whose `info` block holds many blank, indented lines. Finding the title took twice as long with each such line.
- The script sandbox's faker, which `postman-collection` depends on but which was never bundled, is overridden to 10.6.0, past GHSA-qxc2-j82w-r537.
- seroval 1.7.3, which the web app's router depends on, fixes two flaws that let crafted values inject script into serialized output (GHSA-9wx9-5pv9-3349, GHSA-f86p-h4j2-7qgj).
